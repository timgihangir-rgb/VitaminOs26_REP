3.2 Журналирование (write-ahead log)
------------------------------------
[+] 3.2.1: WAL-область на диске (блоки 1..64): кольцевой лог, commit-блоки
           (magic+seq), begin/log/commit/complete
     -> src/wal.rs: блок 1=JSUPER_A, блок 2=JSUPER_B (зеркала с cksum),
        блоки 3..64=62 слота; состояние слота выводится из seq>applied_seq;
        протокол: payload'ы в слоты -> jsuper LOGGED в ОБА зеркала (точка
        фиксации) -> apply в bcache -> jsuper applied_seq=seq (закрытие).
[+] 3.2.2: обернуть все операции с метаданными и данными в транзакции
     -> vfs.rs: mkdir/rmdir/touch/rm/write_file/append/copy/mv через wal_txn
        (успех=commit, ошибка=abort); vitafs.rs: fs_write_block/f_read_block
        маршрутизируют мутации в staging при активной транзакции, чтения
        видят staging (read_through); commit захватывает грязные bcache и
        inode в журнал (ничего не утекает мимо).
[x] 3.2.3: восстановление при монтировании: реплей коммитов по seq, очистка
           лога, fsck-lite - recover()+fsck_lite() в try_mount, офлайн-сверка
           образа (python) подтверждает консистентность битмапов/инодов;
           fsck чинит битмапы после kill -QEMU (проверено в crash-пробах).
[~] 3.2.4: crash-consistency тест: kill QEMU посреди записи → перезагрузка →
           консистентность - убитый тест в test_crash.py (форма底 работает:
           journal replay + fsck проверен), но автотест нестабилен из-за
           ловли промпта на сплэше. ОСЬ ВОССТАНАВЛИВАЕТСЯ - проверено вручную.

БЛОКЕР РЕШЁН (найден и исправлен): "zero-writer" = ПЕРЕПОЛНЕНИЕ KERNEL-СТЕКА
задачи, а не порча памяти посторонним писателем. wal::stage() в debug-сборке
генерирует кадр 0x20b8=8376Б (два 4КБ стек-темпа для `(bno,*buf)` + кортеж),
плюс ~6КиБ цепочки вызовов выше = 33080Б > 32КиБ стека → перелив 312Б ниже
дна свежевыделенного стек-бокса тикера → сносились String-имя (0x31538),
текст log-line (0x314f8), ralloc-заголовок бокса (~0x31550) и низ ЖИВОГО
стека → отложенный GPF (Option::as_ref по мусору 0x53f000ff... из данных
блока) внутри hole::Cursor::try_insert_after. Детерминизм - от фиксированной
раскладки кучи/глубин вызовов при загрузке.
Диагноз за один заход связкой: serial-dump в exception_handler → gdb-watchpoint
на адресе (поймал memcpy dest НИЖЕ бокса со стеком вызова stage) → objdump
замыкания push (lea 0x10a0(%rsp)/0x98(%rsp) = темпы В кадре; rsp при записи =
0x31438 < дно бокса 0x31570). Инструменты: /tmp/opencode/name_watch.py.
ФИКСЫ: (1) scheduler.rs STACK_SIZE 32→64КиБ; (2) wal.rs stage(): Vec::push
заменён на прямую запись в слот через сырой указатель (as_mut_ptr().add +
copy_nonoverlapping + set_len) - оба 4КБ темпа исчезли, кадр схлопнулся.
Верификация: 3 прогона x35c без монитора/gdb: [exc]=0, по 34 полных цикла
WAL-коммитов ([st:len]=0..3 повторяется), тикер живёт.

Найденные и исправленные баги при отладке WAL:
[x] дедлок VFS_LOCK: спин-лок под вытеснением - крутящийся отбирает CPU у
    держателя навсегда -> scheduler.rs vfs_lock_yield (try_lock+hlt)
[x] OOM кучи: резерв staging 104*4КБ=427КБ из 1МиБ кучи -> MAX_STAGING=16,
    CAPTURE_RESERVE=24, try_reserve без паники
[x] неатомарный commit_portion: тик посреди фиксации - чужая транзакция
    мутирует staging, сырые указатели в невалидную память ->
    without_interrupts вокруг порции
[x] алиасинг capture: ссылка &ENTRIES[i].data держалась через stage(),
    apply вытеснял этот же слот кэша и перезаписывал данные ->
    копия в статический буфер до stage
[x] OOB order[] в recover: >62 LOGGED-слотов переполняли массив -> guard
[x] большие буферы на стеке задач (4КБ х4 в цепочке commit) -> статики

Урок: куча ядра под спинлоком - аллокации только с IF=1 (правило из
scheduler::spawn); правило каскадно: весь путь фиксации журнала без
аллокаций внутри without_interrupts (ёмкость резервируется заранее).
